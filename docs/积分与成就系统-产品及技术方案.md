# 积分与成就系统：产品功能与技术实现方案

更新日期：2026-11-07  
状态：方案稿。V1.16 已按本文落地，见 [版本更新](releases/V1.16.md)  
适用项目：练搭子微信小程序

## 1. 目标与设计原则

以训练坚持和教练服务闭环为积分来源，以成就提供阶段性反馈，以积分商城兑换项目服务。第一阶段优先奖励可从现有服务端业务事实确认的行为：按计划完成训练，以及预约课程完成后由教练记录出勤。日记、饮食 AI、身体测量和好友互动可作为后续成就条件，不应在首版引入容易刷分的输入型任务。

设计原则：

1. **积分奖励必须由服务端核实业务事件。** 客户端不得直接提交“给我加分”。
2. **积分账本不可覆盖。** 每次发放、扣减、退款、过期均留独立流水，余额可重算。
3. **一个业务事件只奖励一次。** 重试、并发回调、重复完成不得重复记分。
4. **成就定义可配置、授予不可重复。** 成就可有积分奖励，也可以是负面记录但永不奖励积分。
5. **负面成就不是扣分。** 它用于描述违反规则或未完成状态，可用于反馈、连续性统计或风控；不得因“负面成就”自动从积分余额扣分。
6. **兑换先预占、后交付、再核销。** 服务未成功创建或发放时，积分必须释放或退回。
7. **积分与现有 AI 权益分开。** 现有 `entitlements` 是 AI/订阅能力额度；积分是可兑换货币，二者不能混作同一余额。

## 2. 目标用户与入口

- 学员：查看积分余额、获取记录、成就墙、兑换商城和兑换订单；通过训练和预约闭环累计积分。
- 教练：在现有日程和记录中完成出勤、训练同步等业务动作；不直接修改学员积分。
- 运营：配置积分规则与成就、维护兑换商品、审计账本、处理兑换失败和人工补偿。

建议学员侧入口：

- 「进展」页新增积分概览和成就卡片，跳转积分中心。
- 个人中心增加「积分与成就」。
- 训练完成页和课程闭环页展示本次积分入账结果，重复完成则显示已领取，不重复发放。

建议新增页面：`points` 积分中心、`achievements` 成就墙、`rewards` 兑换商城、`redemption-detail` 兑换详情（也可先合并前三个为单页分段）。运营入口先复用 `/ops/`，不放入教练或学员导航。

## 3. 积分产品规则（首版建议）

以下数值是便于讨论和配置的初始建议，正式上线前应通过运营配置确认，不写死在页面中。

| 事件 | 首版建议分值 | 服务端判定条件 | 防刷规则 |
| --- | ---: | --- | --- |
| 完成计划训练 | +10 | 有效 `WorkoutSession` 状态为 completed，且至少有一个实际完成组；若需严格要求计划训练，session 必须关联已发布 plan/revision | session ID 唯一奖励；每日上限可配置；取消/放弃不奖励 |
| 预约课程闭环 | +20 | booking 为 confirmed，且教练通过现有 attendance 接口记录为 attended；不以预约提交、教练接受或学生自报为完成 | booking ID 唯一奖励；迟到/缺席/取消不奖励；单日上限可配置 |
| 连续训练成就 | 见成就规则 | 按业务日 Asia/Shanghai 汇总有效训练日 | 同一天最多计一个连续日；不因多个 session 增加连续天数 |

积分事件采用 `event_type + source_id + beneficiary_id + rule_version` 去重键。规则变更不自动给历史事件重新发分；若要补发，生成可追溯的补偿流水。

### 3.1 训练完成口径

当前训练服务有 `finalizeSession` 与组状态。建议采用以下首版口径：

- 只奖励学员本人作为受益人的 session。
- 必须 session 最终状态 `completed`，且至少一个 actual set 为 done。
- 同一 session 仅一条训练积分流水，不按组数重复发放。
- 是否必须关联计划：产品描述要求“按照训练计划完成打卡”，因此推荐首版只奖励关联已发布计划的 session；自由训练可只计入训练统计或由后续独立规则奖励。
- session 结束后由服务端领域服务计算奖励；如组次自动完成规则仍未解决，暂缓启用积分规则或先修复并验证完成口径。

### 3.2 预约闭环口径

当前预约状态和 attendance 由 booking 服务管理。首版建议将“闭环”定义为：预约已确认 + 教练记录 attended。以下均不奖励：预约申请、待确认、已拒绝、已取消、改期申请未完成、缺席、仅完成训练记录但未记录出勤。

若日后产品定义要求学生和教练双方确认，可增加双方确认字段；不建议首版用客户端点击作为唯一完成依据。

## 4. 成就系统

成就是条件规则及用户达成记录。建议区分三种呈现类型：

| 类型 | 示例 | 是否发积分 | 说明 |
| --- | --- | --- | --- |
| 正向里程碑 | 首次完成计划训练、完成 10 次计划训练、连续训练 3/7 天、首次完成教练课程闭环 | 可配置固定一次性奖励 | 发放与成就授予必须在同一事务或具备可靠幂等 |
| 正向习惯 | 本月完成 8 次训练、连续 4 周达到目标 | 可奖励一次或周期奖励 | 明确自然月/周口径及每周期上限 |
| 负面/风险提示 | 连续预约未出席、连续多周未完成计划、频繁取消 | **不奖励积分、不自动扣分** | 仅个人提醒或在授权范围内给教练支持性提示；不公开羞辱、不排名 |

每个成就定义至少包含：稳定 `achievement_key`、名称、描述、图标、正/负类型、触发事件、阈值/周期、是否公开展示、积分奖励（负面必须为 0）、规则版本、生效时间和启停状态。

隐私规则：负面成就默认只对本人可见。教练是否可见，沿用现有绑定关系与授权/业务需要；好友动态不默认传播成就。需要分享时由用户主动操作。

## 5. 积分兑换服务

兑换商品是后台维护的服务目录，不是客户端硬编码列表。首批商品可包括：

| 商品 | 交付方式 | 需要的能力/确认 |
| --- | --- | --- |
| 新增训练计划 | 成功创建一份学员拥有的手动计划草稿或经确认的计划服务 | 可复用当前计划创建接口；商品说明清楚是“计划草稿”还是教练定制服务 |
| AI 饮食记录/识别次数 | 发放 `nutrition_scan` entitlement 单位 | 复用现有权益账本的 grant/usage 概念，设置来源为积分兑换，保证幂等；若 AI provider unavailable，兑换不应误导用户认为可识别 |
| 会员开通 | 先定义会员权益包和有效期，再授予订阅 | 现有支付未接入；积分兑换可以是非支付来源的 subscription grant，但需服务端定义可读历史、到期行为及取消规则 |

兑换商品字段建议：`sku`、名称、描述、积分价格、交付类型、参数、可见角色、库存/总量（可选）、每用户限额、启停状态、起止时间、规则版本。

### 5.1 兑换状态机

`created → reserved → fulfilling → fulfilled`

失败路径：

- 预占失败：订单拒绝，不扣分。
- 交付明确失败：订单 `failed`，退还/释放预占积分。
- 交付结果不确定：订单保持 `fulfilling` 或 `needs_review`，禁止自动重复发权益；由幂等交付查询或运营核对。
- 用户主动取消：仅在未开始交付且商品允许取消时释放积分。

积分扣减/退款需分别生成账本流水，不能删除原流水。对支持自动化交付的商品，在同一数据库事务中创建兑换单、预占积分和待执行 outbox 事件；交付成功后核销预占并写 entitlement/subscription/plan 结果。

## 6. 页面与用户流程

### 6.1 积分中心

- 可用积分、累计获得、累计兑换。
- 最近积分流水及筛选（获得/兑换/退款/补偿）。流水展示来源、时间、状态和订单/训练/预约引用。
- 成就进度、已获得成就和可兑换服务入口。

### 6.2 训练奖励流程

学员开始关联计划的训练 → 逐组记录 → 完成 session → 服务端确认有效完成 → 写唯一积分流水 → 评估成就 → 返回积分变化和新成就 → 小程序展示 toast/完成卡片。

### 6.3 课程奖励流程

预约 → 教练确认 → 课程完成 → 教练在 booking attendance 记录 attended → 服务端写积分并评估成就 → 学员下次打开课程/积分中心看到结果。通知可由现有 outbox 投递，但不能阻塞业务事务。

### 6.4 兑换流程

浏览商品和规则 → 查看积分价格、交付说明、有效期/限制 → 二次确认 → 服务端原子预占积分和创建订单 → 执行交付 → 展示结果和订单详情。

## 7. 技术架构建议

### 7.1 新增领域服务

- `pointsService`：账户查询、记账、预占/核销/释放、流水查询、幂等约束。
- `achievementService`：规则读取、事件消费、条件评估、成就授予和奖励发放。
- `redemptionService`：商品查询、创建兑换单、履约、取消、失败退款和订单查询。
- `rewardEventService` 或 `domainEvents`：从训练/预约领域动作生成标准业务事件。

不要让页面直接调用“加积分”接口。训练和预约服务在完成业务状态转移时调用奖励领域服务，或写入可靠 outbox 后由 worker 处理。

### 7.2 关键数据模型

首版 JSON store 可新增以下集合；若迁移数据库，采用对应关系表并建立唯一索引。

```text
pointAccounts
  { userId, available, reserved, lifetimeEarned, lifetimeSpent, revision, updatedAt }

pointLedger
  { id, userId, delta, type, status, sourceType, sourceId,
    idempotencyKey, ruleKey, ruleVersion, relatedOrderId, metadata, createdAt }

achievementDefinitions
  { key, title, description, polarity, trigger, threshold, period,
    pointReward, visibility, version, enabled, startsAt, endsAt }

userAchievements
  { id, userId, achievementKey, definitionVersion, progress, target,
    earnedAt, sourceEventId, rewardLedgerId }

rewardCatalog
  { sku, title, description, pointsPrice, fulfillmentType, fulfillmentPayload,
    enabled, startsAt, endsAt, perUserLimit, stock, revision }

redemptionOrders
  { id, userId, sku, pointsPrice, status, idempotencyKey,
    reserveLedgerId, fulfillmentRef, failureCode, createdAt, updatedAt }

rewardOutbox
  { id, eventKey, eventType, payload, status, attempts, nextAttemptAt, createdAt }
```

账本建议使用 `delta` 正负表达变动，同时保留 `type`（earn/reserve/spend/release/refund/adjust/expire）。预占可用积分时先减少 `available` 并增加 `reserved`；核销时减少 `reserved`，释放时回加 `available`。累计获得不因兑换减少。

### 7.3 API 草案

```text
GET    /points                         当前账户摘要
GET    /points/ledger?cursor=&type=    当前用户积分流水
GET    /achievements                   定义、进度与当前用户达成情况
GET    /rewards                        可兑换商品
POST   /redemptions                    创建兑换（Idempotency-Key 必填）
GET    /redemptions                    当前用户兑换历史
GET    /redemptions/:id                兑换详情

GET    /admin/points/rules             查询/配置积分规则
POST   /admin/points/adjustments       人工补偿或冲正（ticket_id + 审计）
GET/PATCH /admin/achievements/:key     成就定义管理
GET/POST/PATCH /admin/rewards          商品目录管理
GET    /admin/redemptions              失败/待人工核验订单
POST   /admin/redemptions/:id/retry    安全重试履约（须幂等）
```

具体 API 命名应先对照 `server/src/routes/index.js` 现有风格；需要新增权限中间件与请求校验。运营端操作必须 ops-only，补分、冲正、改规则和履约重试要记录操作者、原因、ticket_id 和前后值。

### 7.4 业务事件与幂等键

标准事件建议：

```text
training.session.completed { eventId, sessionId, studentId, planId, planRevision, completedSetCount, occurredAt }
booking.attendance.attended { eventId, bookingId, studentId, coachId, occurredAt }
```

奖励幂等键示例：

```text
points:training_completed:<sessionId>:<ruleVersion>
points:booking_attended:<bookingId>:<ruleVersion>
achievement:<userId>:<achievementKey>:<periodKey>
redemption:<userId>:<clientRequestKey>
```

请求的幂等键不能代替业务唯一约束。数据库層需对奖励来源唯一键、用户成就周期唯一键、兑换用户请求键建立唯一约束；JSON store 至少在 `store.tx()` 内检查并追加，确保单进程并发串行。多进程部署时 JSON 文件锁不够，需要数据库事务和唯一索引。

### 7.5 与现有权益账本关系

- `pointLedger` 管理积分货币；`entitlementService` 管理 AI 次数等能力配额；二者通过兑换订单引用关联。
- 兑换 AI 饮食识别时，积分账本完成兑换扣分，权益账本增加 `nutrition_scan`；随后每次真实识别仍按现有权益规则预占/核销。
- 兑换会员时创建来源为 `points_redemption` 的 subscription/grant 记录，不创建支付单、不伪造支付成功。
- 兑换新增训练计划时，使用计划服务创建资源并记录订单 `fulfillmentRef`。注意训练计划接口当前工作区有未提交的手动创建改动，需先审查并完成既有变更的测试和合并策略。

## 8. 安全、异常与运营规则

- 所有积分奖励以服务端 actor 和受益人关系计算；禁止信任客户端传入积分数、用户 ID、成就 key 或 SKU 价格。
- 预约奖励只能在确认 attended 的服务端状态转移后触发。学员不能通过调用 API 自报出勤。
- 同一事件、成就周期、兑换请求和履约结果必须幂等；失败重试不重复扣分或发放权益。
- 支持 ledger 审计与人工冲正，不允许直接编辑历史余额。人工调整需严格 ops 权限和原因。
- 退课/撤销是否冲回已发积分需产品定规则：建议只有明确的业务纠错（如 attendance 误标）才发反向冲正流水；正常完成后不因后续无关行为扣分。
- 积分有效期首版建议不过期，降低解释和客服成本；若运营以后引入到期，必须提前通知、逐笔标记来源批次并写 `expire` 流水。
- 成就奖励的积分奖励也必须使用积分账本；不能只修改账户余额。
- 不把未出席等负面成就做成公开排行榜或惩罚机制。

## 9. 分阶段实施顺序

### 阶段 0：产品口径确认

确认积分数值、计划训练是否仅限关联计划、每日/每周上限、课程 attended 的权威确认者、负面成就可见范围、积分过期策略、会员商品权益、AI 未开通时的兑换限制。

### 阶段 1：积分账本与两类事件

新增账户摘要/流水；从 session 完成与 booking attended 服务端状态转移发放固定积分；覆盖幂等、重复请求、事务失败和账户隔离。暂不开放兑换。

### 阶段 2：成就引擎

先实现少量事件驱动成就（首次训练、累计训练次数、连续训练天数、首次课程闭环），再加入负面提醒规则。成就定义和用户授予分离，奖励通过 ledger 发放。

### 阶段 3：兑换商城

先上线可可靠自动履约的新增计划草稿；再接 AI 次数与会员 grant。加入预占、履约、核销、失败退款、订单查询和运营审计。

### 阶段 4：运营与分析

在 `/ops/` 增加规则/商品配置、审计、失败订单重试和积分异常监控；补充兑换转化、奖励成本和异常重复事件指标。

## 10. 验收清单

- 完成有效计划训练产生一次奖励；重复 finalize、重复请求、并发触发都只奖励一次。
- 自由训练、未完成、放弃、零完成组、非本人 session 不满足计划训练奖励条件。
- booking pending/confirmed/cancelled/absent 均不奖励；仅有效 attended 奖励一次；教练权限检查生效。
- 训练和预约事件触发成就进度；同一成就和周期只能授予一次；成就奖励写账本。
- 负面成就不增加积分、不扣积分，默认仅本人可见。
- 积分不足无法兑换；重复提交不重复建单/扣分；商品失效或超限可读地失败。
- 履约失败释放积分；履约成功只发放一次；不确定结果进入人工核验，不自动重复发权益。
- AI 商品兑换发放 `nutrition_scan` 权益并有兑换来源；服务不可用时产品明确展示限制。
- 会员兑换不调用真实支付、不伪造支付回调；订阅到期按既有 entitlement 规则处理。
- 运营调整和重试均有权限校验及审计字段；隐私与角色隔离覆盖所有新增查询。
- JSON store 升级兼容旧数据；隔离临时数据的自动化测试不污染真实 `server/data`。

## 11. Vibe coding 提示词

建议按阶段分别提交提示词，不要一次要求模型完成全系统。每次先让模型审查代码和接口，再给小范围实现任务。以下提示词可复制到新任务中。

### 提示词 A：先做代码审计与实施计划

## 12. 推荐的首版决策

为了先形成闭环，建议首版仅启用：计划训练完成 +10、预约 attended +20；正向成就奖励首登/首次训练/累计 10 次等一次性小额积分；负面成就只做个人提醒。积分暂不过期，先开放“新增计划草稿”兑换。AI 饮食次数需确认真实 AI 可用性后再上架；会员兑换要先明确会员包含的服务和期限。所有分值与商品价格均后台配置，先在测试账号和隔离数据中验证。

## 13. 现有实现关联点与待确认风险

- 训练结束：`server/src/services/trainingService.js` 的 `finalizeSession`。
- 预约出勤：`server/src/routes/index.js` 的 `POST /bookings/:id/attendance` 与 `server/src/services/bookingService.js` attendance 实现。
- 权益：`server/src/services/entitlementService.js` 及现有 `/entitlements`、`/usage-ledger`、运营 grant 路由。
- 事务：服务端路由普遍通过 `store.tx()` 修改 JSON store；这适用于当前单实例方案，多实例部署前需迁移到具备事务/唯一索引的数据库。
- 训练完成状态、pending 组自动完成与新课次 session 复用问题在交接文档中列为待解决；积分开发前必须固定奖励口径并为相关路径补测试。
- 当前工作区存在未提交的计划创建改动；兑换计划商品应复用审查后的正式服务接口，不能在奖励代码里直接拼写 store 结构。
