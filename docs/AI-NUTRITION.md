# AI 拍照记饮食 · 预留功能与接入约定

2026-10-22，来源于用户新增需求：从 AI 页直接拍照或选择照片，分析碳水、蛋白质、脂肪并记录，在允许的情况下自动同步绑定教练。

## 本轮已实现的入口

- AI 页第一张工具卡为“拍照记饮食”，包含拍照与相册两个直接入口。
- `/pages/food-photo/index` 支持打开指定来源的微信图片选择器、本地照片预览与重选；取消选择保留已有照片。
- 展示三大营养素的预留结果位，未识别时显示“—”，不填充示例估算值。
- 识别并记录按钮和自动同步开关处于禁用状态，并明确标记待接入。照片只保留在本次页面的临时状态，不上传、不保存为饮食记录。
- 提供手动饮食记录入口。已有体态和目标图模块保持原来的业务接口。

## 后续开发流程

1. 选择食物照片，上传到本人私有媒体空间。真实图片上传成功之前不能把“媒体登记”当成上传完成。
2. 创建营养识别任务，提供排队、识别中、失败与重试状态。未配置供应商时明确不可用，不返回成功或伪造营养数值。
3. 返回食物明细、识别份量、碳水／蛋白质／脂肪估算及不确定信息。三大营养素单位为克，区分每 100g、单份与整餐总量；禁止混淆口径。
4. 用户确认或修正食物、份量、餐次与日期后，幂等保存为本人饮食记录。识别失败或只选择照片，不写饮食记录。未知值保留为空，不当作 0。
5. 仅在服务端重新验证条件后，将允许共享的该条记录提供给当前教练，并进入现有饮食点评流程。

## 营养结果建议结构

最终字段由 AI 与服务端实现共同确认，可采用：

```json
{
  "task_id": "...",
  "media_id": "...",
  "status": "needs_confirmation",
  "items": [{
    "food_name": "...",
    "portion": { "amount": null, "unit": "g", "is_estimated": true },
    "macros_g": { "carbs": null, "protein": null, "fat": null },
    "basis": "identified_portion",
    "uncertainties": []
  }],
  "total_macros_g": { "carbs": null, "protein": null, "fat": null },
  "is_estimate": true,
  "model_version": "..."
}
```

保存时还需由服务端确定本人身份，并保留用户确认后的日期、餐次、修改后的值、来源任务与估算标识。用户不能通过客户端传入别人的 ID 写入饮食记录。

## 自动同步的授权边界

- 有效教练绑定、有效饮食授权、用户主动开启“自动同步”，三者同时成立。默认关闭，不复用“曾经共享过一天”作为持续授权。
- 自动同步设置应绑定用户及当时的教练关系；换教练、解绑或撤回授权后立即停止，不自动转给新教练。
- 保存与共享应分别可查：饮食保存成功但同步失败时显示“已记录，尚未同步”，不能诱导重复保存。异步发送和重试前再次检查授权。
- 只同步获准的这条营养记录；原图默认不共享，需要单独授权。朋友模块不接收饮食、照片或营养数据。
- 现有日记共享按“日期＋类别”控制，会开放当天整类内容。不得为了同步一条 AI 饮食记录，静默调用整天共享并连带公开其他手动记录；接入时需增加逐条共享能力，或另行清楚征得整天共享同意。
- 停止自动同步只影响后续自动发送；已共享内容的撤回使用独立、明确的操作，保留本人记录。

## 接入后的验收要点

拍照／相册取消与拒绝、无食物或多餐／模糊照片、份量不明、未知营养值、人工修正、重复保存、旧任务迟到、跨账号、供应商不可用、授权关闭、解绑或换教练、保存成功但同步失败、原图与朋友隔离。

本轮不实现真实营养模型、图片上传、营养持久化或自动同步，避免与若芷负责的 AI 模块产生重复实现。

验证：30 个 WXML、32 个 WXSS 通过微信官方编译器，JavaScript / JSON 检查通过；模拟器已确认 AI 页新增工具卡、拍照／相册入口及待接入说明。未在用户设备上拍摄或选择实际照片，真机选图与预览仍待体验验证。
